# SQL：カーディナリティ・選択率・インデックス・N+1問題

## 1. カーディナリティ（Cardinality）

### 用語の意味
カラムに含まれる異なる値の種類の数。

### 本質理解
値の種類が多いか少ないかを表す指標。

例：

| user_id | gender |
|---|---|
| 1 | 男性 |
| 2 | 女性 |
| 3 | 男性 |
| 4 | 女性 |

- user_id：カーディナリティが高い
- gender：カーディナリティが低い

一般的に、値の種類が多いカラムは検索対象を絞り込みやすい。

## 2. 選択率（Selectivity）

### 用語の意味
検索条件によって、全レコードのうち何割が該当するかを表す割合。

### 本質理解
検索結果が全体に対してどれくらい少ないかを表す。

例えば、100万件のデータから1,000件が該当する場合：

```text
選択率 = 1,000 / 1,000,000
       = 0.001（0.1%）
```

- 選択率が低い：検索対象が少ない
- 選択率が高い：検索対象が多い

一般的に選択率が低い条件は、インデックスによる検索効率が高くなりやすい。

※ カーディナリティが高いことと選択率が低いことは関連する場合があるが、同じ意味ではない。

## 3. インデックスが効かないケース

### 用語の意味
インデックスを作成していても、SQLの条件やデータの分布などによって、データベースがインデックスを利用しない、または利用しても効率が悪くなる状態。

### 本質理解
インデックスは必ず利用されるわけではない。

オプティマイザが実行コストを判断し、フルテーブルスキャンなどを選択する場合がある。

### 主なケース

| ケース | 例 |
|---|---|
| 前方一致以外のLIKE | `LIKE '%abc'` |
| カラムに関数を適用 | `WHERE YEAR(created_at) = 2026` |
| 暗黙の型変換 | カラムと検索値の型が異なる |
| 選択率が高い | 大量のレコードが該当する |
| 複合インデックスの順序 | 先頭カラムを検索条件に含めない |

### 改善例

変更前：

```sql
SELECT *
FROM users
WHERE YEAR(created_at) = 2026;
```

変更後：

```sql
SELECT *
FROM users
WHERE created_at >= '2026-01-01'
  AND created_at < '2027-01-01';
```

カラムに関数を適用せず、範囲条件にすることでインデックスを利用しやすくする。

※ 実際にインデックスが利用されるかはDBMSや実行計画による。

## 4. N+1問題

### 用語の意味
関連データを取得する際に、最初の1回のSQLに加えて、レコードごとに追加SQLが発行される問題。

### 本質理解
必要なデータをまとめて取得せず、レコードごとに繰り返し取得することでSQLの実行回数が増加する。

### 発生例

usersテーブルからユーザーを取得し、それぞれの投稿を取得する場合。

```php
$users = User::all();

foreach ($users as $user) {
    echo $user->posts;
}
```

ユーザーが100人の場合：

```text
ユーザー取得：1回
投稿取得：100回

合計：101回
```

### 解決方法：Eager Loading（事前読み込み）

```php
$users = User::with('posts')->get();

foreach ($users as $user) {
    echo $user->posts;
}
```

```text
ユーザー取得：1回
投稿取得：1回

合計：2回
```

### 本質
Eager Loadingによって関連データをまとめて取得し、SQLの発行回数を削減する。

## 5. 全体の関係性

| 用語 | 本質 |
|---|---|
| カーディナリティ | 値の種類の多さ |
| 選択率 | 検索結果が全体に占める割合 |
| インデックス | 検索を効率化する仕組み |
| N+1問題 | SQLの過剰な繰り返し実行 |
